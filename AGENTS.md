# disc: тестирование воспроизведения DISC-теста

## Цель workspace

Здесь мы проверяем, насколько точно LLM **по одному запросу воспроизводит
готовый продукт** — тест DISC школы менеджмента Stratoplan — как
самодостаточное HTML-приложение:

- **чистая генерация** — один сырой user-запрос → один ответ модели:
  готовый HTML-файл;
- **без харнеса** — никаких агентных циклов, инструментов, файловых
  операций; модель не запускает и не проверяет свой код;
- **без подсказок** — никакого system prompt и few-shot; задание и
  эталонные данные (снятые с оригинала) одинаковы для всех моделей;
- оригинал изучен заранее и разобран в эталон: механика визарда, все 24
  вопроса со служебными типами d/i/s/c, алгоритм подсчёта, особенности
  (включая странности оригинала — их воспроизводим как есть).

## Git-процесс (важно)

Любые правки попадают в `main` **только через pull request**:
ветка → коммиты → push → PR → ревью → мерж. Прямые коммиты и пуш
в `main` запрещены всегда и всем — включая правки, сделанные ассистентом:
ассистент открывает PR, а не коммитит в `main`. Один PR — одна тема.

**Мерж — только после явного апрува владельца** (Дмитрий): ассистент
открывает PR и останавливается — ждёт одобрения. Нажимать merge без прямого
подтверждения владельца в чате запрещено; «молчание» или автономный режим
апрувом не считаются. Пока у репо нет remote, правило действует как
конвенция для локальных веток; после первого push на GitHub — закрепить
ruleset на `main` (без force-push и удаления ветки).

Сестринский workspace — `~/MyProjects/Models/` (собесы LLM, карта знаний
PHP): конвенции хранения, изоляция прогонов и судейство перенесены оттуда;
сервер моделей тот же.

## Сервер моделей

Все модели берём с ollama на внутреннем сервере (адрес — env
`OLLAMA_BASE_URL`, локальное значение — в `.env.local`, см. следующую
секцию):

- список: `curl "$OLLAMA_BASE_URL/api/tags"`
- детали: `curl "$OLLAMA_BASE_URL/api/show" -d '{"name":"<тег>"}'`
- генерация: `curl "$OLLAMA_BASE_URL/api/generate"` (или `/api/chat`)

Локальный ollama этой машины для тестов **не используется**.

## Окружение запусков (env, вне git)

Скрипты не содержат внутренних адресов, путей и ID — всё берётся из env
(в git только нейтральные дефолты). Локальные значения — `.env.local` в корне
workspace: в git не попадает (шаблон — `.env.local.example`), скрипты
подхватывают его при старте автоматически, переменные из профиля шелла
главнее. Сами ключи в `.env.local` не лежат — только пути к файлам с ними
(файлы вне workspace, не шарить). При незаданной переменной скрипт падает
с подсказкой, какую переменную задать.

## Структура

- `test-assignment/` — только методология тестового задания (**никаких
  результатов**):
  - `TASK.md` — задание, которое получает модель (канонический текст);
  - `reference/original.md` — изученное описание оригинала: поток,
    подсчёт баллов, токен и страница результата, особенности оригинала;
  - `reference/questions.json` — эталон данных: 24 вопроса с прилагательными
    и служебными типами (из `data-type` оригинала);
  - `prompts/prompt.json` — собранный промпт прогона (TASK + данные);
    версионированный объект `{"version": N, ...}`; изменение задания = +1
    версия, старая рядом как `prompt.vN.json`;
  - `rubrics/scorecard.md` — рубрика оценки (4 оси, шкала 0–4) и план
    машинных проверок;
  - позже здесь же: раннеры и чекеры (`runner*.py`, `check.py`,
    `judge*.py`). Никаких результатов в этой папке.
- `models/` — одна папка = одна уникальная модель (по дайджесту весов).
  - Имя папки = тег модели, где `:` и `/` заменены на `-`
    (пример: `huihui_ai/Qwen3.8-abliterated:latest` →
    `huihui_ai-Qwen3.8-abliterated-latest`);
  - для облачных моделей — слаг провайдера с `/` → `-`
    (пример: `openai-gpt-6-luna/`);
  - одни и те же веса под разными тегами — одна папка, оба тега перечислены
    в её `model.md`;
  - внутри папки модели:
    - `model.md` — карточка: источник, архитектура, параметры, квант,
      контекст, дайджест, статус и наблюдения;
    - `test-assignment/run-XX/` — прогоны (XX — двузначный номер с нуля):
      `session.json` (полный протокол: промпт+версия, ответ, параметры
      генерации, тайминги, usage), `solution/index.html` (файл решения,
      извлечённый из ответа), позже `check.json` (машинные проверки) и
      вердикты судей;
    - `test-assignment/scorecard.md` — свод по всем прогонам этой модели.
- `reports/` — кросс-модельные своды (`COMPARE.md`, `REPORT.md`, таблицы)
  и бухгалтерия платных API (`spend.csv`, в git не живёт).

## Правила тестирования (важно)

1. Один прогон = один сырой промпт → один ответ. Без system-сообщения,
   инструментов, уточняющих диалогов и ретраев «до правильного ответа».
   Прямой вызов API предпочтительнее `ollama run`, чтобы ничего лишнего
   не подмешивалось.
2. Промпт не подгоняется под модель. Неудачный результат — это результат,
   а не повод менять задание; изменение задания = новая версия промпта
   и новая серия.
3. Параметры генерации — дефолтные модели, если для серии не оговорено
   иное; seed не фиксируется. Нестандартные параметры (температура, think)
   фиксируются в `session.json` и в `model.md`.
4. Модель выгружается из памяти до и после каждого прогона — прогоны
   изолированы (KV-кэш между прогонами не переиспользуется).
5. Устойчивость: стандарт серии — 5 прогонов на модель, минимум 3;
   каждый с нуля, сравнивается постоянство результата и разброс баллов.
6. Сначала машинные проверки (структура, баланс, дубликаты, ключ) —
   они бесплатны и объективны; LLM-судьи подключаются только к тому,
   что машиной не проверяется.
7. Судья изолирован: один ответ → один запрос судьи, без истории между
   оценками. Судьи яруса 2 запускаются только скриптом (когда появится) —
   не сабагентами сессии и не через платные ручные вызовы.
8. Каждая платная операция журналируется в `reports/spend.csv`
   (модель, цель, запросы, токены, стоимость) — сверяться перед прогонами.
9. Результаты живут только в папках моделей; методология
   (`questionnaire/`) результатов не содержит.
10. Язык заметок и промптов — русский (если конкретный тест не требует
    иначе).

## Методика: воспроизведение DISC-теста (кратко)

Подробно — `test-assignment/reference/original.md` (оригинал) и
`test-assignment/rubrics/scorecard.md` (оценка). Кратко:

- один прогон = модель получает промпт из `prompts/prompt.json` (задание +
  эталонные данные) и возвращает один HTML-файл; файл сохраняется как
  `solution/index.html` в `run-XX` модели;
- **машинные проверки** (до судей): решение — один файл; нет внешних
  запросов и отправки данных; все 24 вопроса и прилагательные совпадают с
  эталоном посимвольно; смоук в headless-браузере — пройти тест скриптом по
  контрольной раскладке и сравнить показанные баллы с эталонным пересчётом
  (инвариант: сумма баллов четырёх типов = 0);
- **судейство**: 4 оси — data (точность данных), logic (подсчёт),
  ux (работоспособность), impl (качество и ограничения), каждая 0–4;
  ярус 1 — decision-модель по рубрике, ярус 2 — сильный изолированный судья
  (или владелец); судья обязан приводить примеры;
- **устойчивость**: стандарт серии — 3–5 прогонов на модель; сравниваются
  решения между собой (структура кода, приёмы реализации) и разброс баллов;
- версия промпта пишется в `session.json` поле `"prompt"`.
