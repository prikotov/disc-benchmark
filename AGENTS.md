# disc: тестирование копирования веб-приложения агентом

## Цель workspace

Здесь мы изучаем способность LLM-агента **самостоятельно сделать копию
веб-приложения** по ссылке на источник:

- тестовое задание — **перенос функционала DISC-теста** школы менеджмента
  Stratoplan в копию: одностраничное HTML-приложение, без бэкенда и без
  отправки результатов на почту;
- **модель собирает материалы сама**: ей выдаётся только задание и ссылка
  на источник; она сама изучает страницу и код, сама извлекает данные
  (24 вопроса со служебными типами d/i/s/c), алгоритм подсчёта и поведение
  интерфейса, сама строит решение;
- **прогон — агентная сессия в pi**: модель работает инструментами по
  умолчанию (bash с доступом в сеть, файловые операции) в чистой рабочей
  директории; никаких подсказок сверх задания, задание одинаково для всех
  моделей;
- оригинал снят в эталон (снимок исходников, данные вопросов, описание
  механики, включая странности оригинала — их воспроизводим как есть);
  эталон служит только судьям и машинным проверкам, модели его не отдаём;
  сравниваем копию с оригиналом: насколько верно она работает и насколько
  качественно сделан перенос.

## Git-процесс (важно)

Любые правки попадают в `main` **только через pull request**:
ветка → коммиты → push → PR → ревью → мерж. Прямые коммиты и пуш
в `main` запрещены всегда и всем — включая правки, сделанные ассистентом:
ассистент открывает PR, а не коммитит в `main`. Один PR — одна тема.

**Мерж — только после явного апрува владельца** (Дмитрий): ассистент
открывает PR и останавливается — ждёт одобрения. Нажимать merge без прямого
подтверждения владельца в чате запрещено; «молчание» или автономный режим
апрувом не считаются. Пока у репо нет remote, правило действует как
конвенция для локальных веток; после первого push на GitHub — закрепить
ruleset на `main` (без force-push и удаления ветки).

Сестринский workspace — `~/MyProjects/Models/` (собесы LLM, карта знаний
PHP): конвенции хранения, изоляция прогонов и судейство перенесены оттуда;
сервер моделей тот же.

## Сервер моделей

Все модели берём с ollama на внутреннем сервере (адрес — env
`OLLAMA_BASE_URL`, локальное значение — в `.env.local`, см. следующую
секцию):

- список: `curl "$OLLAMA_BASE_URL/api/tags"`
- детали: `curl "$OLLAMA_BASE_URL/api/show" -d '{"name":"<тег>"}'`
- генерация: `curl "$OLLAMA_BASE_URL/api/generate"` (или `/api/chat`)

Локальный ollama этой машины для тестов **не используется**.

## Окружение запусков (env, вне git)

Скрипты не содержат внутренних адресов, путей и ID — всё берётся из env
(в git только нейтральные дефолты). Локальные значения — `.env.local` в корне
workspace: в git не попадает (шаблон — `.env.local.example`), скрипты
подхватывают его при старте автоматически, переменные из профиля шелла
главнее. Сами ключи в `.env.local` не лежат — только пути к файлам с ними
(файлы вне workspace, не шарить). При незаданной переменной скрипт падает
с подсказкой, какую переменную задать.

## Правила тестирования (важно)

1. Один прогон = одна агентная сессия: модель получает только задание
   (промпт из `prompts/prompt.json`) и работает в чистой рабочей
   директории. Никаких подсказок и материалов сверх задания, никаких
   уточняющих диалогов и ретраев «до правильного результата» — всё
   необходимое модель добывает сама.
2. Инструменты агента — дефолтные pi (bash с доступом в сеть, файловые
   операции): ничего не отключаем и не добавляем — одинаковые условия
   для всех моделей. Транспорт — pi с моделью на сервере
   (`OLLAMA_BASE_URL`), не `ollama run`.
3. Промпт не подгоняется под модель. Неудачный результат — это результат,
   а не повод менять задание; изменение задания = новая версия промпта
   и новая серия.
4. Параметры генерации — дефолтные модели, если для серии не оговорено
   иное; seed не фиксируется. Нестандартные параметры (температура, think)
   фиксируются в `run.json` и в `model.md`.
5. Прогоны изолированы: чистая рабочая директория на каждый прогон,
   сессии между прогонами не переносятся; модель выгружается из памяти
   до и после прогона (KV-кэш не переиспользуется).
6. Устойчивость: стандарт серии — 5 прогонов на модель, минимум 3;
   каждый с нуля, сравнивается постоянство результата и разброс баллов.
7. Сначала машинные проверки (структура, данные, подсчёт, ограничения) —
   они бесплатны и объективны; LLM-судьи подключаются только к тому,
   что машиной не проверяется.
8. Судья изолирован: один ответ → один запрос судьи, без истории между
   оценками. Судьи яруса 2 запускаются только скриптом (когда появится) —
   не сабагентами сессии и не через платные ручные вызовы.
9. Каждая платная операция журналируется в `reports/spend.csv`
   (модель, цель, запросы, токены, стоимость) — сверяться перед прогонами.
10. Результаты живут только в папках моделей; методология
    (`test-assignment/`) результатов не содержит. Файлы, оставленные
    агентом в run-каталоге (скачанные исходники источника, собственные
    тест-скрипты, черновики) — не недостаток и не удаляются: это след
    исследования и материал под возможные доработки; решение —
    `index.html`.
11. Язык заметок и промптов — русский (если конкретный тест не требует
    иначе).
12. **Контейнмент**: bash агента имеет полный доступ к файловой системе —
    выход за пределы workdir возможен и наблюдается (qwen3.8 off создал
    run-99 в репозитории; ornith писал test-файл в reference/source).
    После каждого прогона: `git status` + проверка посторонних файлов в
    методологии/эталоне; заблудившиеся файлы переносить в
    `run-XX/escape-evidence/` как evidence, в выводах фиксировать.

## Методика: копирование DISC-теста (кратко)

Сводное описание всего конвейера (промпт дословно, запуск pi, проверки,
судья, агрегация) — `reports/METHOD.md`; подробно —
`test-assignment/reference/original.md` (оригинал) и
`test-assignment/rubrics/scorecard.md` (оценка). Кратко:

- один прогон = агентная сессия pi (`test-assignment/runner.py`): рабочая
  директория агента — временный каталог вне репозитория (в контекст агента
  не попадает ни AGENTS.md, ни эталон); промпт — из `prompts/prompt.json`
  (задание + ссылка на источник); артефакты копируются в `run-XX`:
  `run.json` (условия), `pi-session/` + `pi-run.log` (след), `index.html`
  и прочие файлы агента; эталон (`questions.json`, `original.md`, снимок
  `reference/source/`) модели недоступен — качество самостоятельного
  изучения источника оценивается судьями и машинными проверками (как
  модель изучала источник — видно по трейсу `pi-session`);
- **машинные проверки** (до судей, `test-assignment/check.py` →
  `check.json`): решение — `index.html`; нет внешних запросов и отправки
  данных; все прилагательные совпадают с эталоном посимвольно;
  отображение (текст, тип) сравнивается с эталоном как мультимножество
  пар (повторяющиеся прилагательные с разными типами); рендер-смоук
  в headless Chrome (DOM отрисовался, нет Uncaught); симуляция полного
  прохождения с замером баллов — следующий шаг (браузерная автоматизация),
  а пока баллы проверяют судьи по коду/вручную;
- **судейство**: 4 оси — data (точность данных), logic (подсчёт),
  ux (поток и работоспособность), impl (качество и адаптации), каждая 0–4;
  ярус 1 — decision-модель по рубрике, ярус 2 — сильный изолированный судья
  (или владелец); судья обязан приводить примеры;
- **устойчивость**: стандарт серии — 3–5 прогонов на модель; сравниваются
  решения между собой (структура кода, приёмы реализации) и разброс баллов;
- версия промпта пишется в `run.json` поле `"prompt"`.

## Идея следующего задания (записано 2026-11-17, волна 4)

**«Исправленное приложение»**: то же тестовое задание для локальных моделей, но
с явным указанием на известные расхождения оригинала с методикой DISC
(15 позиций, сверка с «Surrounded by Idiots» — таблица в REPORT.html, секция 5).
Модель должна построить приложение с типами, исправленными по методике
(и, возможно, прочими правками: email-шаг, результат на той же странице).
Метрика «заметил → исправил → сообщил» из REPORT.html здесь становится
основной: проверяется, видит ли модель несоответствия сама, как исправляет
и оповещает ли. Эталонные пары для чека — отдельно (исправленный questions.json).

## Идея волны 5 (записано 2026-11-18): DISC-команда строит «правильный тест»

**Исследовательский вопрос: можно ли через DISC-роли управлять поведением агентов
в мультиагентной среде?** Родился из волны 4 + аудита эталона по книге Эриксона.

**Задание команде**: реализовать «правильный тест» — исправленную версию DISC-теста
(типы по методике книги, не как у Stratoplan; см. эталон волны 4 — исправленный
questions.json). Команда локальных моделей, каждому участнику выделена роль.

**Два условия (A/B)**:
- **A «DISC»**: роль описана через DISC-профиль с поведенческими паттернами
  («ты D — инициируешь, решаешь быстро, режешь споры; ты C — проверяешь данные,
  требуешь точности, сомневаешься в неподтверждённом» и т.д.);
- **B «без DISC»**: та же роль описана поведенчески нейтрально, без DISC-словаря
  («ты отвечаешь за инициативу и решения», «ты отвечаешь за проверку данных»).

Если поведение команд A и B различается значимо — DISC-словарь управляет поведением;
если нет — DISC здесь лишь декорация к обычному role-prompting.

**Роли**: по командным ролям Белбина (Руководитель, Генератор идей, Оценщик,
Реализатор, Завершатель и т.д.); каждой роли добавляется DISC-профиль участника —
это и есть варьируемый слой A/B. Привязка «роль → модель» и конкретные профили —
решение владельца; прямое «тип = должность» не используется.

**Модели**: локальные с волны 1–2 из «добротного» лагеря (huihui, qwen3.8, orcarouter,
bonsai) — по одной на роль; оркестрация через pi-сессии с общим каталогом прогона
(файлы как среда обмена, сообщения — через файлы-письма или общий лог).

**Метрики**:
1. продукт: «правильный тест» против исправленного эталона (чек волны 4);
2. **поведенческие**: соответствует ли фактическое поведение агента описанию роли
   (D — доля инициативных сообщений/решений; C — доля найденных им расхождений;
   S — доля правок консистентности; I — коммуникация) — сравнение A vs B;
3. самооценки ролей: знает ли агент в конце, кем «был» (условие A).

**Признак успеха**: значимое расхождение поведения A/B при одинаковых задачах —
тогда «управление через DISC» возможно; идентичное поведение — DISC = декорация.

**Конкретизация (2026-11-24)**: идея оформлена в задание `team-assignment/`

## Методика: анкета DISC (кратко)

Второй тип эксперимента: модель **отвечает** на анкету — 24 вопроса из книги
Томаса Эриксона «Кругом одни идиоты» (в книге подаётся как «блиц-тест»),
ничего не строит. Цель — насколько модель разбирается в DISC: точность,
стабильность, влияние уровня мышления, токены. Сводное описание —
`quiz/README.md`. Кратко:

- транспорт — **прямые вызовы ollama** (`/api/chat` для chat-моделей,
  `/v1/systemone` для decision-моделей clef/clef-flash): не pi и не агентная
  сессия, инструментов нет; правила про инструменты агента не применяются,
  остальные (дефолтные параметры генерации, seed не фиксируется, честная
  фиксация событий, контейнмент) действуют;
- промпт: блиц-тест без упоминания книги и автора (решение владельца),
  вопросы **без вариантов ответов**; chat-модель отвечает JSON «номер
  вопроса → ответ», decision-модель — argmax по кандидатам в noul-пробах
  (+ метрика калибровки p_correct); уровни мышления — только существующие
  по `/api/show`, 5 прогонов на модель×уровень;
- балл машинный (нормализация + словарь синонимов ключа,
  `quiz/reference/key.json`), судьи не нужны; флаги честности:
  skipped/unparsed/ambiguous/near — «не распознано» не равно «неверно»;
- английская серия (quiz-en): анкета и ключ — из английского оригинала
  (23 вопроса; русский вопрос про болезненную реакцию на критику в
  оригинале отсутствует), облачные — по отдельному распоряжению владельца;
- отчёт — `reports/QUIZ.md/.html`, общий для обоих языков: сводная таблица
  модель×язык×уровень (сортировка кликом, дефолт — по правильности),
  матрица модель×язык×уровень×вопрос, раздел «Язык: ru vs en» (Δ по
  процентам — множества вопросов разные), проблемные вопросы; сравнение
  chat (открытый ответ) и decision (argmax по кандидатам) — межформатное,
  помечается оговоркой.

## Набор моделей и уровни мышления

Проверено на сервере `/api/show` 2026-11-14. Правила уровней:

- **Унификация**: для моделей с градациями серия — три точки: `off`
  (без мышления), `low` (лёгкое), `default` (дефолтный уровень при включённом
  мышлении). Для моделей с ручкой только вкл/выкл — `off / on`.
- **ollama**: уровень — поле `think` верхнего уровня тела `/api/chat`
  (`false` / строка уровня), не в `options`.
- **облака**: стандарт серии — `reasoning_effort: low` (сравнимо с `low`
  локальных; так же в сестринском workspace).
- уровень и факт эскалации фиксируются в `run.json`; если провайдер не
  отдал запрошенный уровень (как pi эскалирует off → low у alibabacloud)
  — прогон относится к фактическому уровню.
- стандарт серии — 3 прогона на (модель × уровень), минимум 3; для дорогих
  облачных — 1–2.

### Операционные уроки для агентных прогонов (из карточек сестринского workspace)

Карточки моделей перенесены из `~/MyProjects/Models` дословно (с пометкой
провенанса и пустым разделом «disc»); результаты других задач в выводы
не переносятся, но операционные наблюдения их агентного этапа 2 применимы
напрямую:

- **серверное окно контекста**: тег без `num_ctx` даёт фактическое окно
  32768 — для агентных прогонов брать теги `-pi-100k` / `-ctx100k`
  (num_ctx 102400); поэтому в матрице только они;
- **pi**: лимит выхода 32768 токенов на один ответ; у heavy-thinking
  моделей бюджет может уйти целиком в размышления (bonsai-2 medium:
  «Response was truncated») — следить за обрывами в `pi-run.log`;
- **qwen3.8** на агентном задании: лестница перевёрнута — low лучший,
  medium чуть хуже, off ≈ max хуже; ollama молча заменяет «high» дефолтом
  medium — уровень «high» не запускать;
- **muse-glimmer**: уровень мышления безразличен (low ≈ max), самая
  быстрая в сетке; **bonsai-2**: паралич на агентной работе во всех
  thinking-режимах, код пишет только off — для неё это и есть предмет
  проверки;
- **gemma4-26b**: бимодальность — ранние самовыходы за ~1 минуту в 2 из 3
  прогонов; ранний exit — валидный результат прогона, а не сбой раннера;
- **deepseek-flash**: снапшоты модели меняются по датам — фиксировать
  версию в `run.json` при прогоне;
- **ornith**: ручки `think` в `/api/show` нет — off делается через
  `enable_thinking` (qwen-механика шаблона), фактический уровень
  фиксировать в `run.json`.
