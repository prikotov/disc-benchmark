# Методика: как тестируются модели (сводный отчёт для проверки)

Обновлено 2026-11-14. Документ описывает весь конвейер — от промпта до
отчёта — чтобы можно было проверить методику до запуска остальных моделей.
Всё описанное реализовано и отработано на пилоте huihui (10 прогонов,
run-01…10).

## 1. Что тестируем

**Задание модели** (дословно отправляется в промпте, файл
`test-assignment/prompts/prompt.json`, версия 3 — единственный источник):

```text
# Тестовое задание: сделать копию веб-приложения

Сделай копию теста DISC, размещённого на странице школы менеджмента
Stratoplan.

**Источник**: https://stratoplan-school.com/disc/

Изучи страницу и её код самостоятельно, собери всё необходимое и перенеси
функционал.

## Что нужно сделать

Одностраничное HTML-приложение — копия теста с этой страницы, работающее так
же, как оригинал: пользователь проходит тест шагами, ранжирует варианты
перетаскиванием, в конце видит свои баллы.

## Требования к копии

1. Один самодостаточный файл `index.html`: все стили и скрипты инлайн.
2. **Без бэкенда и без отправки данных куда-либо.** Шаг сбора email и
   переход на отдельную страницу результата из оригинала убрать: после
   завершения теста баллы показываются в том же приложении.
3. **Без внешних запросов**: без CDN и внешних библиотек, приложение
   работает офлайн, открывается локально (`file://`).
4. Данные теста и поведение интерфейса — как в оригинале; язык интерфейса —
   русский; визуальное оформление — на твоё усмотрение.
5. Иконки — инлайн SVG, растровые изображения не нужны.
6. Целевые браузеры — актуальные Chrome, Firefox, Safari.

## Формат результата

Рабочий `index.html` в текущей директории. Пояснения не нужны.
```

**Важно про чистоту**:

- модель получает **только этот текст** — никаких исходников и эталона
  (в v1 промпта были готовые данные, в v2 — встроенные исходники; обе
  версии архивированы как deprecated, v3 — текущая);
- модель **сама** идёт по ссылке, сама скачивает страницу и скрипты, сама
  извлекает 24 вопроса, служебные типы d/i/s/c и алгоритм подсчёта;
- рабочая директория агента — временный каталог **вне репозитория**: в
  контекст не попадает ни AGENTS.md workspace, ни эталон
  (`test-assignment/reference/`), ни чужие результаты;
- эталон (24 вопроса со служебными типами, алгоритм, странности оригинала —
  `reference/questions.json`, `reference/original.md`, снимок
  `reference/source/`) существует **только для проверок и судейства**.

## 2. Как запускается pi (`test-assignment/runner.py`)

Адаптация проверенного `runner_pi.py` сестринского workspace
(`~/MyProjects/Models/test-assignment/backend/billing/`).

**Команда агента** (дословно):

```bash
pi -p \
  --session-dir <run-XX>/pi-session \
  --model <тег> \
  --thinking <off|low|medium> \
  "<текст задания из prompts/prompt.json>"
```

env: `PI_CODING_AGENT_DIR=<tmp>/pi-home` (изолированный конфиг — глобальный
`~/.pi/agent` не используется), `PI_OFFLINE=1` (pi не ходит в сеть сам —
сеть использует только инструмент bash агента, например `curl` к источнику).

**models.json на лету** (в `<tmp>/pi-home`):

```json
{"providers": {"ollama": {
  "baseUrl": "http://nserv:11434/v1",
  "api": "openai-completions", "apiKey": "ollama",
  "models": [{
    "id": "huihui-ai:pi-100k",
    "contextWindow": 102400, "maxTokens": 32768,
    "reasoning": true,
    "thinkingLevelMap": {"off": "none", "minimal": "low", "low": "low",
                         "medium": "medium", "high": "xhigh",
                         "xhigh": "xhigh", "max": "xhigh"}
  }]}}}
```

- `thinkingLevelMap` строится **из фактической шкалы модели** (`/api/show` →
  `thinking.values`): несуществующие уровни ollama молча подменяет дефолтом,
  поэтому мапим только существующие; off → `none`; для булевых шкал
  (false/true — orca, gemma4) любой не-off уровень — строка `"high"`
  (ollama трактует как true); pi-уровень max → нативный максимум шкалы.
- `maxTokens`: 8192 по умолчанию, **32768**, если в шкале модели есть
  энергичный максимум (xhigh/max) — иначе thinking выжигает бюджет в пустой
  ответ (наблюдение сестринского workspace, bonsai-2 medium).
- `contextWindow: 102400` — для агентных прогонов берутся теги
  `-pi-100k`/`-ctx100k`: теги без `num_ctx` дают фактическое окно сервера
  32768 (проверено `/api/ps` на bonsai-2 и muse-glimmer).

**Изоляция и управляемость**:

- pi — лидер собственной process group: SIGTERM/таймаут (3600 с) гасят всю
  группу, «зомби-pi» невозможен; `pi-run.log` пишется стримингом;
- фоновый поток раз в 30 с опрашивает `/api/ps`: чужая модель в VRAM во
  время прогона = конкуренция → факт пишется в `run.json`
  (`ollama_contention`), такие прогоны исключаются из метрик;
- рабочая директория — `/tmp/disc-pi-*/run`, после прогона **все** созданные
  агентом файлы копируются в `run-XX` (в т.ч. скачанные исходники — это
  след исследования, не недостаток; решение владельца 2026-11-14).

**Артефакты прогона** (`models/<модель>/test-assignment/run-XX/`):

| файл | содержимое |
|---|---|
| `run.json` | модель, thinking (запрошенный + фактическая шкала), контекст, maxTokens, версия и sha промпта, время, exit code, killed, список файлов агента, конкуренция VRAM |
| `pi-session/*.jsonl` | полный след сессии: ходы, размышления, вызовы инструментов, usage |
| `pi-run.log` | stdout/stderr pi |
| `index.html` + прочее | решение и рабочие файлы агента |
| `check.json`, `playthrough.json`, `session-stats.json`, `judge-tier1.json`, `summary.md`, `screenshots/` | пост-обработка (ниже) |

## 3. Серия и уровни мышления

- уровни: **off / low / default**(дефолтный включённый; у huihui это medium,
  у muse — high); для булевых шкал — off/on; облака — `reasoning_effort: low`;
- **3 прогона на (модель × уровень)** — стандарт; минимум 3; для дорогих
  облачных 1–2; seed не фиксируется, прогоны изолированы (чистая рабочая
  директория, модель выгружается после прогона);
- фактический уровень фиксируется в `run.json`; если провайдер эскалировал
  (pi эскалирует off → low у alibabacloud) — прогон относится к
  фактическому;
- xhigh/max-уровни в серию не включаются: пробный huihui xhigh дал те же
  16/16 при ×2–4 цене (run-10).

## 4. Проверки после прогона

### 4.1 Машинный чек (`check.py` → `check.json`, до судей)

1. **Самодостаточность**: в `index.html` нет внешних запросов (CDN-скрипты,
   fetch/XHR/sendBeacon/WebSocket/EventSource, внешние img/link/css-url,
   form action) **и локальных зависимостей** (`<script src="disc.js">` —
   нарушение «одного файла»; найдено на huihui run-02 до исправления
   чекера).
2. **Данные посимвольно**: все прилагательные из эталона присутствуют
   (84 уникальных текста). Известные опечатки оригинала (латинская «c» в
   «Экспресcивный» — косяк Stratoplan) нормализуются: **исправление их
   моделью — плюс, не провал** (решение владельца 2026-11-14); факт
   отклонения фиксируется (`known_quirk_normalized`).
3. **Типы (текст+тип)**: извлекаются из разметки/данных решения (форматы:
   `data-type`-разметка, JS-объекты с полными ключами `type/text`, короткими
   `t/l/w`, JSON-ключи в кавычках, массивы пар — в обоих порядках) и
   сравниваются с эталоном **как мультимножество** — повторяющиеся
   прилагательные с разными типами («Настойчивый» d,d,i) ловятся.
4. **Рендер-смоук**: headless Chrome (`--dump-dom`): DOM отрисовался,
   кнопка есть, ноль Uncaught-ошибок.

### 4.2 Автопрохождение (`playthrough.mjs` → `playthrough.json` + скриншоты)

Драйвер в headless Chrome: старт → находит видимые «списки-вопросы»
(контейнер с 4 детьми, набор текстов совпадает с эталонным вопросом —
без привязки к тегам, с нормализацией известных опечаток и ранговых
префиксов «1…») → переставляет пункты → «Далее»/«Завершить тест» → экран
результата. Скриншоты `start/step/result.png` — для отчёта и судьи.

**Честное ограничение** (эксперименты 2026-11-14, три способа ввода):
симуляция drag&drop **невоспроизводима** на произвольных реализациях
(Pointer Events, откат SortableJS, скролл-контейнеры) — показанные баллы
фиксируются справочно, логику подсчёта проверяет судья по коду. Поток
(старт → шаги → результат) драйвер проверяет надёжно: на huihui все 9
серийных прогонов — 24/24 вопроса.

### 4.3 Судья яруса 1 (`judge.py` → `judge-tier1.json`)

- модель: **glm-5.3-flash** (z.ai, через pi; судья — не кандидат, см.
  AGENTS.md); изолированный вызов: один ответ → один вердикт,
  `--no-context-files`, cwd — каталог прогона;
- судья получает: рубрику (`rubrics/scorecard.md`), эталон данных,
  машинные проверки, автопрохождение, статистику сессии и **полный код
  решения**; обязан **вручную проследить алгоритм подсчёта** на контрольной
  раскладке (инвариант суммы баллов = 0) и привести примеры по каждой оси;
- вердикт: JSON, 4 оси × 0–4 (data — точность данных, logic — точность
  подсчёта, ux — поток и работоспособность, impl — ограничения и
  адаптации), итог 0–16;
- политика осей: рабочие файлы агента не штрафуются; исправление известных
  опечаток источника — плюс; tier 2 (обзор владельца/сильного судьи) —
  после машинного яруса.

## 5. Агрегация и отчёты (`report.py`)

- `--run <dir>` → `<run>/summary.md` (условия, токены, чеки, судья) +
  строка в `models/<модель>/test-assignment/scorecard.md` (дедуп по
  прогону);
- `--all` → `reports/RUNS.md` — таблица всех прогонов всех моделей;
- `--html` → `reports/RUNS.html` — визуальный отчёт: карточки прогонов со
  скриншотами (инлайн), машинными метриками и вердиктами; клик по
  скриншоту — просмотр 1:1;
- по завершении полной модели — `reports/MODEL-<имя>.md` (лестница уровней,
  провалы, сравнение с рейтингом карты знаний — см. `MODEL-huihui.md` как
  образец) и свод в `reports/FORECAST.md` (предрегистрация прогноза от
  2026-11-14: ранжирование моделей и проверка мета-вопроса «переносится ли
  рейтинг карты знаний на агентную задачу»).

## 6. Правила честности (кратко)

1. Промпт не подгоняется под модель; изменение задания = новая версия
   промпта и новая серия.
2. Условия одинаковы: изолированный pi-home, одна и та же команда,
   дефолтные параметры генерации, seed не фиксируется.
3. Эталон и методология недоступны агенту (проверено устройством стенда:
   workdir вне репозитория).
4. Нестандартные события (таймаут, killed, конкуренция VRAM, эскалация
   thinking) фиксируются в `run.json` и видны в отчётах.
5. Платные вызовы (облачные модели) журналируются в `reports/spend.csv`.
6. Всё сырьё открыто: сессии, логи, код решений хранятся в прогонах.
