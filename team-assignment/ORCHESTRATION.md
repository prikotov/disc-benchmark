# Оркестрация командного прогона

Один прогон = одна команда = одна сессия тимлида pi + ролевые сабагенты.
Транспорт — pi с моделями на сервере (`OLLAMA_BASE_URL`), роли запускаются
через расширение `subagent` (пример в поставке pi:
`examples/extensions/subagent`): каждый сабагент — отдельный процесс pi
с изолированным контекстом, своей моделью из frontmatter и стримингом
в сессию тимлида. Тимлид вызывает инструмент `subagent` (одиночные задачи,
параллельные до 8, цепочки с `{previous}`).

## Подготовка прогона (раннер, будет написан)

1. Рабочая директория прогона — **временный каталог вне репозитория**
   (как в `test-assignment/runner.py`): в контекст агентов не попадают
   ни AGENTS.md, ни эталон, ни карточки моделей.
2. Изолированный pi-home прогона: расширение `subagent`, агенты ролей —
   `roles/*.md` с подстановкой `{{model}}` из `team.json` (уровень мышления
   модели — по правилам серий workspace).
3. В рабочую директорию кладутся только материалы задания: `TASK.md`
   и `questions.json` (приложение к заданию). Эталонные материалы
   для судей (`test-assignment/reference/`) команде недоступны.
4. Окружение: переменные `DISC_*` (см. `INFRA.md`) пробрасываются
   в сессию; значения секретов в промпты не входят.
5. Имя версии продакшена (`disc-v-<имя версии>`) владелец согласует
   до старта; фиксируется в `run.json` и журнале команды.
6. Модели выгружаются из памяти до/после прогона (KV-кэш не переиспользуется);
   фоновый наблюдатель VRAM — как в одиночных прогонах.

## Общая среда команды

Рабочая директория — единственная среда обмена:

- `app/` (или иное имя по решению architect) — код продукта;
- `team/journal.md` — журнал: план, решения, распределение задач,
  приёмки, исправления данных, отчёты ролей;
- `team/mailbox/<роль>/` — письма между ролями (файлы);
- `team/architecture.md`, `team/review-<N>.md`, `team/test-report.md`,
  `team/deploy.md`, `team/final-report.md`, `team/qa/` — артефакты ролей.

Тимлид видит стриминг сабагентов и их итоговые отчёты; полные сессии
сабагентов сохраняются в pi-home прогона (след для судей и метрик).

## Рекомендуемый поток (тимлид вправе адаптировать)

1. **Анализ**: architect разбирает задание и данные, строит архитектуру
   и контракты (`team/architecture.md`); devops параллельно выясняет
   окружение сервера.
2. **Разработка**: frontend и backend работают параллельно по контрактам.
3. **Ревью**: reviewer проверяет бэкенд против задания; правки — backend,
   повторное ревью.
4. **Интеграция и локальные проверки**: tester проверяет поток, баллы,
   почту (контрольный ящик), мобильность.
5. **Деплой**: devops деплоит на `https://ai-aid.pro/disc-v-<имя версии>/`.
6. **Проверка прода**: tester повторяет ключевые проверки на проде —
   это финальный критерий «продукт создан».
7. **Финал**: тимлид пишет `team/final-report.md`, прогон завершается.

## Правила и ограничения

- Инструменты — дефолтные pi, ничего не отключаем и не добавляем
  (кроме расширения `subagent` как транспорта ролей).
- Промпт задания не подгоняется под модели; неудачный прогон — результат.
- Параметры генерации — дефолтные модели, уровень мышления фиксируется
  в `run.json` по правилам серий workspace.
- Деплой — только devops, только в согласованный путь `/disc-v-<имя версии>/`;
  правки общих конфигов сервера — стоп и эскалация владельцу.
- Письма — только на контрольный ящик `DISC_TEST_MAILBOX` при проверках;
  боевой поток приложения отправляет на email пользователя (это функция
  продукта, не нарушение).
- Секреты не печатать; чекер сканирует следы сессий на утечки значений.
- **Контейнмент**: после прогона — `git status` репозитория + проверка
  посторонних файлов в методологии/эталоне; заблудившиеся файлы —
  в `run-XX/escape-evidence/`, факт фиксируется в выводах.

## Хранение результатов

Командный прогон хранится в `team-runs/<слаг состава>/run-XX/`
(2026-11-26: вынесено из `models/_teams/…` — команда не модель).

**Слаг состава** — из поля `slug` в `team.json` (например `team-alpha`);
смена модели в роли = новый состав = новый слаг (`team-beta`, …) и новая
серия прогонов. Каталог слага:

- `team.json` — машиночитаемый состав на серию (роль → модель → уровень;
  копия утверждённого `team-assignment/team.json`, `status: approved`);
- `team.md` — человеческая карточка состава: дата, условие (A —
  DISC-профили / B — нейтральные роли), таблица ролей → моделей →
  фактические уровни (из `/api/show` на момент прогона), ссылки на
  карточки моделей, наблюдения;
- `run-XX/` — прогон (XX с нуля, двузначный):

- `run-XX/run.json` — условия: слаг состава + копия состава, версия
  промпта (`team-assignment/prompts/prompt.json`), имя версии
  продакшена, параметры, время;
- `run-XX/pi-session/` — сессия тимлида; `run-XX/agent-sessions/` —
  сессии сабагентов (по ролям); `run-XX/pi-run.log`;
- `run-XX/workspace/` — рабочая директория команды (в песочнице — `/work`;
  код продукта, артефакты) — след хода работы, не чистится;
- `run-XX/deploy-evidence/` — скриншоты и логи прода, письмо-доказательство;
- `run-XX/check.json`, `run-XX/judgments/` — машинные проверки и вердикты;
- `run-XX/escape-evidence/` — при выходах за пределы workdir
  (в песочнице невозможны, проверка остаётся как контроль корректности).

В карточке каждой модели-участника (`models/<модель>/model.md`, раздел
«disc») — ссылка на командные прогоны с её участием. Кросс-командные
своды — в `reports/`.

## Серии и устойчивость

- Единица сравнения — **состав команды** (роли → модели). Стандарт серии —
  3 прогона на состав (командные прогоны дорогие; минимум и изменения
  утверждает владелец).
- Смена модели в роли = новый состав = новая папка `team-runs/<слаг>`.
- Устойчивость: сравниваются продукты между прогонами и разброс баллов;
  поведенческие метрики ролей (см. рубрику) — между прогонами и составами.
- A/B-серия (будущее): условие A — DISC-словарь в ролях (текущие карточки),
  условие B — нейтральные описания тех же ролей; задание и состав идентичны.
