# Рубрика оценки командного прогона (scorecard)

Продукт и процесс оцениваются по четырём осям, каждая 0–4 (итог 0–16).
Судья обязан приводить конкретные примеры (фрагменты кода, строки
журнала, наблюдения на проде) в обоснование каждой оси. Машинные проверки
(`check.json`) делаются до судей и передаются судье вместе с материалами.

Материалы судье: код продукта (`workspace/`), журнал и отчёты ролей
(`workspace/team/`), следы сессий тимлида и сабагентов, `check.json`,
`deploy-evidence/` (скриншоты прода, письмо), `run.json` (состав, условия).

## Оси

### 1. SPEC — соответствие заданию (анкета, подсчёт, поток)

Данные анкеты посимвольно против `reference/questions.json` (канонический
исправленный эталон; самовольные правки формулировок и типов — дефект); типы d/i/s/c не видны
пользователю; подсчёт серверный и строго по алгоритму (+1 верх, −1 низ,
средние 0; инварианты диапазона и суммы); полный поток: старт → 8 шагов →
email → результат; интерпретация индивидуальная и на русском; письмо
содержит баллы и интерпретацию.

- **4** — все требования задания выполнены точно, контрольные раскладки
  сходятся с эталонным пересчётом.
- **2** — в целом верно, единичные расхождения (≤3 прилагательных/типов,
  краевой дефект подсчёта, интерпретация слабо зависит от баллов).
- **0** — данные перевраны/сокращены, алгоритм неверен, типы показаны
  пользователю, поток не проходим до результата.

### 2. PROD — продакшен и работоспособность

Приложение задеплоено на согласованный адрес
`https://ai-aid.pro/disc-v-<имя версии>/` и реально там работает:
прохождение, подсчёт, интерпретация, письмо проверены на проде;
корректная работа на мобильном и десктопе; деплой-дисциплина соблюдена
(только свой путь, чужое не тронуто).

- **4** — прод работает end-to-end, мобильность и десктоп без дефектов,
  деплой чистый и задокументирован (инструкция + откат).
- **2** — прод доступен, но есть дефекты (мобильная вёрстка разваливается,
  почта/LLM работают через раз, деплой с огрехами).
- **0** — не задеплоено, прод не работает, либо тронуты чужие части сайта.

### 3. QUALITY — инженерное качество

Symfony-проект: структура, читаемость, валидация входа, безопасность
(секреты только из окружения, не в репозитории/логах; XSS/инъекции),
обработка недоступности LLM; ревью reviewer реально состоялось
(отчёты с примерами, правки по дефектам); тесты backend и проверки tester
реально выполнены, а не декларированы.

- **4** — код чистый, ревью и тесты состоялись с артефактами, секретов
  в следах нет, отказоустойчивость LLM реализована.
- **2** — код рабочий, но запутанный/с мёртвыми кусками; ревью или тесты
  формальные; единичные огрехи безопасности без утечки секретов.
- **0** — секреты в коде/репозитории/следах, ревью и тестов не было,
  код неработоспособен.

### 4. TEAM — процесс и роли

Оркестрация тимлида: план, распределение задач, приёмка по критериям,
разрешение конфликтов, продукт доведён до done. Роли работают в своих
зонах, артефакты ролей на месте (архитектура, ревью, отчёт tester,
деплой-инструкция, финальный отчёт). Поведение участников соответствует
DISC-профилям ролей (см. поведенческие метрики); журнал отражает реальные
решения, а не декорацию.

- **4** — процесс управляем, все роли включены по назначению, конфликты
  решены, поведение узнаваемо по профилям, журнал содержательный.
- **2** — процесс шёл, но с перекосами (тимлид писал код сам, роль
  выпала, ревью/тесты пропущены и не восстановлены, журнал формальный).
- **0** — оркестрации не было (один агент сделал всё или продукт
  не собран), роли игнорировались.

## Итог

Сумма осей 0–16. Формат вердикта (JSON в `judgments/`):

```json
{"spec": 0, "prod": 0, "quality": 0, "team": 0, "total": 0,
 "notes": "…", "examples": "…"}
```

Судья яруса 1 — изолированный вызов decision-модели (glm-5.3-flash,
адаптация `test-assignment/judge.py`); ярус 2 — сильный изолированный
судья или владелец. Один прогон → один запрос судьи, без истории.

## Машинные проверки (план, `check.py` → `check.json`)

1. **Данные**: извлечь данные анкеты из продукта (фикстуры/шаблоны/БД),
   сверить посимвольно с исправленным эталоном (`reference/questions.json`).
2. **Подсчёт**: контрольные раскладки через API/бэкенд (или headless-
   прохождение): баллы против эталонного пересчёта, инварианты
   (диапазон, сумма = 0, средние позиции не влияют).
3. **Прод-смоук**: GET продакшен-адреса (200, ассеты, TLS), headless-
   прохождение на проде, скриншоты мобильной и десктопной ширины.
4. **Почта**: проверочное письмо на `DISC_TEST_MAILBOX` содержит баллы
   и интерпретацию.
5. **LLM-интерпретация**: два разных профиля → разные тексты; при
   выключенном LLM — баллы на месте, честное сообщение.
6. **Секреты**: скан репозитория продукта и следов сессий на значения
   секретов из окружения.
7. **Контейнмент**: `git status` workspace + посторонние файлы
   в методологии/эталоне репозитория бенчмарка.

## Поведенческие метрики ролей (из следов сессий)

Справочно к оси TEAM и для будущей A/B-серии (DISC-словарь vs нейтральные
роли): по сессии каждого сабагента считаются

- **D**: доля инициированных предложений/решений, эскалаций, случаев
  «взял и сделал» против ожидания указаний;
- **I**: объём и инициативность коммуникации (письма, обращения к ролям);
- **S**: доля правок консистентности, планомерность (итерации без
  скачков), доведение задач до конца;
- **C**: число найденных расхождений/дефектов с примерами, требования
  подтверждений, проверочные действия.

Метрики считаются скриптом по JSONL-следам (адаптация `session_stats.py`),
сравниваются между прогонами и составами; значимое расхождение A/B —
предмет отдельной серии, не этого прогона.
