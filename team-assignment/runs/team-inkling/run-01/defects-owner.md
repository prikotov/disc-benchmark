# Дефект, найденный владельцем при ручном тесте (2026-11-26/27)

Симптом: «Почта недоступна…» — и очень долгий ответ; пользователь кликал
кнопку многократно.

## Механика (проверено по коду и замером)

1. **Одиночный запрос = ~15.7 с** (замер 2026-11-27, свежий POST
   `/test/finish`: генерация интерпретации inkling'ом ~600 токенов).
2. **php -S однопоточен** (dev-сервер, которым команда запускала
   приложение): запросы обрабатываются строго последовательно. N кликов
   = N запросов в очереди = последний ждёт N × 15 с.
3. **Каждый брошенный клиентом запрос дорабатывает сервер до конца**
   (curl к ollama, CURLOPT_TIMEOUT = 120 с): клики накапливают нагрузку,
   даже если пользователь ушёл со страницы.
4. Фронтенд дизейблит кнопку сабмита на время ожидания (test.js:132),
   но: прогресса/спиннера нет — «кнопка мёртвая» выглядит как зависание;
   после любой ошибки кнопка ре-энаблится и клики начинают новые POST'ы.

## Классификация

- UX: нет индикатора ожидания; поведение при повторных кликах не
  спроектировано (dedup/cache одинаковых профилей отсутствует).
- Архитектура: синхронный LLM-вызов в цикле запроса + однопоточный
  dev-сервер =queued amplification. Для прод-действительности (полный
  прогон с деплоем) нужен либо быстрый путь (кэш интерпретаций по
  профилю), либо асинхронная выдача.

## Дефект 2 (2026-11-27): интерпретации обрываются на полуслове

- `LlmInterpreter.php`: `'max_tokens' => 1200` при промпте «5–8 абзацев» —
  модель регулярно упирается в лимит, `finish_reason=length`, текст рвётся
  (замер: 2149 символов, обрыв «…но заранее до»).
- Бэкенд не проверяет `finish_reason` и не продолжает генерацию —
  обрезанный текст отдаётся пользователю как валидная интерпретация.
- Ожидание от следующих прогонов: снять/поднять кап + проверка
  finish_reason (или continuation), иначе — честная пометка «текст
  сокращён лимитом».
